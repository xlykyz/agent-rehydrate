# State Schema

状态层目录结构与格式规范。每个子目录的用途、格式约定、写回规则。

---

## 目录概览

```
state/
├── _schema.md          ← 本文档
├── logs/               ← 执行历史
│   └── development-log.md
├── tasks/              ← 当前工作状态
│   └── status.md
├── memory/             ← 稳定事实
│   └── project-context.md
└── wiki/               ← 结构化知识
    └── _index.md
```

---

## logs/

**用途**：记录每次执行的历史。发生了什么、为什么、结果如何。

**格式**：每个任务一条日志，按时间顺序追加。

```
## [YYYY-MM-DD HH:mm] 简短标题

- Context: 任务背景/触发原因
- Action: 执行了什么操作
- Result: 结果（成功/失败/部分完成）
- Files: 涉及的文件列表
```

**规则**：
- 只追加，不修改已有记录
- 每条日志与一次任务执行对应
- 涉及 memory/wiki 写入的，在日志中注明

---

## tasks/

**用途**：管理当前工作状态。

**格式**：单个文件 `status.md`，使用 GFM 任务列表标记。

```
# Tasks

## Priority 0（当前）
- [ ] 事项描述 [P0]
- [/] 进行中的事项 [P0]

## Priority 1（待办）
- [ ] 事项描述 [P1]

## Priority 2（将来）
- [ ] 事项描述 [P2]

## Done（本 session）
- [x] 已完成事项
```

**规则**：
- 只保留活跃事项和本 session 已完成事项
- 跨 session 的历史完成记录归入 `logs/`
- 优先级标记：`[P0]` 阻塞/紧急，`[P1]` 重要，`[P2]` 低优先级

## memory/

**用途**：存放稳定、经过验证、可复用的项目级事实。

**写入条件（必须同时满足）**：
1. 信息稳定（经过至少 2 次不同任务验证）
2. 可复用于当前任务之外的场景
3. 在 `logs/` 中有对应的验证记录

**格式**：一个或多个 `.md` 文件，按主题组织。

```
## 项目事实标题

- 事实陈述 1
- 事实陈述 2
- 来源：log 引用路径
- 验证次数：N
```

**禁止写入**：
- 临时判断或单次观察
- 未验证的假设
- 执行过程细节（归 logs）
- 当前任务状态（归 tasks）

---

## wiki/

**用途**：结构化领域知识与概念模型。

**写入条件**：当结构化知识积累到可独立成文时，创建新的 `.md` 文件。

**格式**：按主题独立文件，如 `wiki/data-model.md`、`wiki/glossary.md`。

```
# 主题名称

## 概念说明

简明定义。

## 关键细节

- 要点 1
- 要点 2

## 相关引用

- 关联文件路径
```

**规则**：
- 每个文件覆盖一个独立主题
- 内容应具备参考价值，而非临时笔记
- `_index.md` 作为目录索引

---

## docs/

**用途**：架构决策与设计文档。

**格式**：
- `decisions.md` — ADR 格式，每个决策独立条目
- `architecture.md` — 架构说明
- `audits/` — 第三方审计报告归档

**规则**：
- 每个重要决策记录为 ADR（日期/背景/决策/理由/影响）
- 不存放代码文档（归 code/）
- 不存放临时笔记（归 logs/）
