# AGENTS.md v2.0 开发文档

> 本文档记录 v2.0 协议的设计背景、架构决策与实现思考。
> 协议文件本体请见 `AGENTS-v2.0.md`，各 skill 实现请见 `skills/`。

---

## 一、为什么要有 v2.0

### v1.0 的问题

| 问题 | 表现 |
|------|------|
| **协议本体过大** | 211 行，所有操作细节内嵌在 AGENTS.md 中，难以维护和复用 |
| **业务逻辑与协议耦合** | 初始化步骤、写回规则、格式规范全部写在协议文件里 |
| **state 目录过重** | tasks/（主观进度）、memory/（主观判断）引入了不可验证的状态层 |
| **入口流程不弹性** | 无论项目状态如何，Agent 都得读完所有 state 目录才能开工 |

### v2.0 的解法

- **协议文件瘦身**：只留哲学 + skill 引用，不嵌入操作细节（211 行 → ~60 行）
- **操作外置到 skill**：每个标准操作封装为独立 skill，协议只引用路径
- **state 精简**：仅保留客观层（logs + wiki），去掉主观层（tasks, memory）
- **入口智能分流**：rehydrate skill 判断当前项目状态，决定初始化还是直接恢复认知

## 二、架构总览

```
AGENTS.md v2.0（协议本体，~60 行）
  │
  ├── 引用 skill 体系
  │     ├── rehydrate/  ← 入口，检查 + 分流
  │     ├── init/       ← 初始化
  │     ├── log/        ← 写日志
  │     └── wiki/       ← 维护知识
  │
state/ → 实际路径为 `.agent/_state/`（下划线前缀避撞，点目录隐式隔离）
├── logs/     ← 执行历史（客观、不可变）
└── wiki/     ← 项目认知（结构化、稳定）
```

### 入口流程

```
Agent 进入项目
     │
     ▼
加载 rehydrate skill
     │
     ├── 未初始化 ──→ init skill
     │                   ├── 创建目录结构
     │                   ├── 复制模板文件
     │                   ├── 阅读项目 → 建立初版 wiki
     │                   └── 写第一条日志
     │
     └── 已初始化 ──→ 加载 wiki（恢复认知）
                     └── 加载 logs（了解上下文）
                              │
                              ▼
                            开工
                              │
                              ├── log skill → 追加执行记录
                              └── wiki skill → 新增/修改知识
```

## 三、四个 Skill 的设计

### 3.1 rehydrate（入口）

**职责**：判断项目状态，决定下一步操作。

- 检查 `.agent/_state/` 是否存在、是否有模板文件、是否有日志
- 若未初始化 → 调 init skill
- 若已初始化 → 加载 wiki + logs，恢复 Agent 认知
- rehydrate 不执行任何写操作，只做判断和加载

### 3.2 init（初始化）

**职责**：将空白项目转化为可工作的状态驱动项目。

- 创建 `.agent/_state/logs/`、`.agent/_state/wiki/`
- 从 `.agent/skills/init/templates/` 复制模板文件
- 阅读项目 `README.md`、代码结构 → 生成初版 wiki（首次知识沉淀）
- 写第一条日志

### 3.3 log（日志）

**职责**：向 `.agent/_state/logs/development-log.md` 追加执行记录。

- 单文件追加模式，不支持修改已有记录（不可变性）
- 格式：`[YYYY-MM-DD HH:mm] action description`
- 每次操作后强制写入（一致性规则）

### 3.4 wiki（知识维护）

**职责**：维护 `.agent/_state/wiki/` 中的结构化项目知识。

- 支持新增、修改、更正
- 写入条件：已验证、可复用的信息
- 不存放假设、单次观察、临时判断

## 四、关键设计决策

### 4.1 为什么 state 只保留 logs + wiki？

v1.0 的 tasks（主观进度）和 memory（主观判断）引入了不可验证的状态层：
- tasks 的"进行中"、"已完成"是 Agent 的自我报告，外部无法验证
- memory 的"经过两次验证"条件难以在单 Agent 体系内严格执行

v2.0 将这两层**推迟**，MVP 只保留客观层：logs（发生了什么）和 wiki（项目是什么）。Agent 的认知通过 rehydrate 从这两层重建。

### 4.2 为什么用 skill 而不是内嵌逻辑？

- **可维护**：修改操作细节不需要动协议文件
- **可扩展**：新增操作（如 task、memory）只需加新 skill
- **可复用**：同一 skill 体系可用于多个项目

### 4.3 为什么 rehydrate 不做写操作？

单一职责。rehydrate 是"门卫"——只判断、加载、分流。写操作全归 init 等下层 skill。如果 rehydrate 既检查又初始化，职责边界模糊，后续扩展困难。

### 4.4 为什么用单文件 log 而非按日期拆分？

MVP 原则。单文件 `development-log.md` 足够覆盖早期项目的日志需求。按日期拆分（`log/2026/05/16.md`）或有明确的分页需求时再升级。

### 4.5 为什么调度约定放在 AGENTS.md 而非 rehydrate skill？

log 和 wiki skill 只定义**怎么做**（格式、追加规则、文件结构、维护操作），不定义**什么时候做**。

"什么时候写日志"、"什么时候更新 wiki"是运行时调度问题，需要**整个会话期间都有效**。rehydrate 只在进入时加载一次，放进去的话 Agent 进入工作状态后就失去了这个约定。

所以调度约定放在 AGENTS.md 协议本体中——它是 Agent 进入项目时就读的指令，整个会话都在上下文里。好处：

- **生命周期匹配**：协议始终有效，rehydrate 只在入口有效
- **单一责任**：skill 只关心 how，rehydrate 只关心 entry，AGENTS.md 关心 when
- **可调性**：修改调度策略不需要改动任何 skill

## 五、边界与限制（当前 MVP）

### 已包含
- ✅ 协议本体（~60 行，纯引用）
- ✅ rehydrate / init / log / wiki 四个 skill
- ✅ 模板文件（_schema.md, development-log.md, _index.md）
- ✅ 入口分流流程

### 未包含（推迟到 v3.0 或按需引入）
- ⏳ `.agent/_state/tasks/` — 任务管理系统
- ⏳ `.agent/_state/memory/` — 稳定事实库（严格验证机制）
- ⏳ 多 Agent 协同场景
- ⏳ 日志自动分页/归档
- ⏳ wiki 全文索引
