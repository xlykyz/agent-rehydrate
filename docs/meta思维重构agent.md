# 元思维重构 AGENT.md 项目说明书（Project Spec）

版本：v1.1

---

# 1. 项目背景（Problem Statement）

在当前的 AI 编程工具生态中，以 Codex、Claude Code 等为代表的 Agent 已经具备相当强的代码生成与修改能力。它们可以快速完成函数编写、模块重构，甚至多文件级别的工程修改。

但在真实的长期开发场景中，一个更隐蔽但更关键的问题逐渐显现出来：

> **AI 在“单次任务执行”上是强的，但在“跨任务、跨时间的一致性”上是弱的。**

从工程视角来看，这意味着每一次调用 Agent，它都像是一个“刚进入项目的新开发者”，需要重新建立对项目的整体理解。这种理解并不是局部的，而是系统性的，包括结构、进度、历史决策以及信息可信度的划分。

因此，每次交互都会重复发生一件成本极高但又不可避免的事情：重新解释项目。

这种不断“重新解释世界”的过程，构成了长期开发中最大的隐性成本——**状态重建成本（State Rehydration Cost）**。

本项目正是针对这一问题提出的一种结构化解决方案。

---

# 2. 项目目标（Objective）

本项目并不试图构建一个新的 AI Agent，也不试图改变现有 Codex 或 Claude Code 的能力边界。

它的目标更加基础，也更加工程化：

> **通过重构 AGENT.md，使其成为一个稳定的“项目级状态重建协议”，让任何 AI Agent 都可以在进入项目时快速恢复一致的认知状态。**

换句话说，本项目关注的不是“让 AI 更聪明”，而是“让 AI 更快进入正确的工作状态”。

这个目标可以拆解为三个核心方向：

首先，是降低 AI 每次进入项目时的理解成本，让“冷启动”变得轻量而可控。

其次，是统一不同 AI Agent 在同一个项目中的行为方式，从而避免结构理解和语义解释的漂移。

最后，是让项目状态能够以文件形式稳定存在，而不是依赖模型的隐式记忆或临时上下文。

---

# 3. 核心设计思想（Design Philosophy）

## 3.1 从 Prompt 到 Protocol

传统的 AGENT.md 通常被当作“提示词集合”，用于指导模型如何回答问题或如何修改代码。

在这种范式下，AGENT.md 更像是一组行为建议，而不是系统约束。

但在本项目中，它的角色发生了根本变化：

它不再是“告诉模型怎么做”，而是“定义模型如何进入这个项目”。

也就是说，它从 prompt 进化为 protocol——一种行为与状态的契约。

---

## 3.2 从智能驱动到状态驱动

在传统范式中，系统依赖模型的即时推理能力来维持一致性。

但在本设计中，一致性不再主要依赖“智能”，而是依赖结构本身。

具体表现为：

- 所有关键状态外置到文件系统中，而不是存放在模型记忆中
- 所有历史通过 logs 显式记录，而不是隐式存在于上下文
- 所有长期知识通过 memory 与 wiki 固化为可恢复结构

因此，模型的职责发生变化：它不再“记住一切”，而是每次都“重新读取一切”，并基于这些结构恢复认知。

---

## 3.3 Repo 即唯一现实

在这个系统中，仓库本身成为唯一可信的现实来源。

不存在隐式状态，也不存在模型侧的持久记忆。

所有认知必须从以下结构中恢复，而不能依赖任何外部假设：

- /state/logs
- /state/tasks
- /state/memory
- /state/wiki
- /state/docs

这种设计使得系统具备可恢复性、可迁移性，以及跨模型一致性。

---

# 4. 系统架构（System Architecture）

整个系统由三层构成，每一层职责清晰且不可混合。

---

## 4.1 协议层（AGENT.md）

这一层是整个系统的核心，但它并不直接存储数据，而是定义规则与行为边界。

它回答三个关键问题：

- 这个项目是什么结构
- AI 应该如何读取项目状态
- 如何正确更新与写回状态

从系统角度看，它更像“运行规则手册”或“状态访问协议”，而不是业务逻辑本身。

---

## 4.2 状态层（/state）

这一层是真正承载项目演化的地方，也是系统的唯一事实来源。

所有信息被明确分类，以避免语义污染与结构混乱：

- logs 记录已经发生的事实与执行过程
- tasks 记录当前正在进行的工作与状态变化
- memory 保存稳定且经过验证的事实性知识
- wiki 保存结构化知识与概念模型
- docs 保存架构决策与设计理由

这种划分的核心意义在于：

> 避免所有信息混杂在一起，从而导致项目状态不可恢复。

---

## 4.3 工作层（/code 与 /docs）

这一层是系统的输出层，用于承载最终的工程成果。

- code 对应具体实现
- docs 对应设计说明与架构解释

它们共同构成项目的“结果形态”，但不参与状态管理逻辑。

---

# 5. Rehydration Protocol（状态重建机制）

系统最关键的机制是“状态重建”，即 AI 每次进入项目时如何恢复认知。

这个过程可以理解为一次系统性的“世界重建”。

首先读取 tasks，从而理解当前正在进行的工作与进度。

然后读取 memory，用于获取稳定且经过验证的基础事实。

接着读取 docs，以理解系统架构与历史设计决策。

必要时再读取 wiki，用于补充更高层的概念结构与知识背景。

完成这一过程后，AI 才进入实际执行阶段。

这一机制的本质是：

> 不让 AI 依赖“记忆”，而是每次都从结构中重新构建项目认知。

---

# 6. Execution Loop（执行闭环）

系统中的所有操作都遵循一个固定闭环，以确保状态一致性。

首先是对当前状态的理解，其次是制定最小可执行计划，然后执行变更，最后将结果写回状态系统。

这种结构的关键在于“最小变更原则”，避免大范围重构导致状态失真或语义漂移。

---

# 7. 与传统 Agent 模式的对比

从行为模式上看，两者有本质差异。

传统 Agent 更像是“增强型代码编辑器”，每次任务都是独立的、短生命周期的操作。

而本系统中的 Agent 更像是“持续参与同一个项目的开发者”，每次进入都基于已有状态继续演化。

两者最核心的区别可以用下表更清晰地表达：

| 维度 | 传统 Agent | 你的协议系统 |
| --- | --- | --- |
| 状态归属 | 人脑 | repo |
| 生命周期 | 单次任务 | 长期项目 |
| 上下文 | 临时 | 可恢复 |
| 行为模式 | 执行指令 | 状态演化 |
| 文档作用 | 无/弱 | 核心组成 |
| 适用场景 | feature级修改 | 项目级开发 |

传统模式依赖即时理解，而本系统依赖状态恢复。

传统模式中项目认知是临时生成的，而本系统中项目认知是可持续重建的。

# 8. 项目定位（Positioning）

本项目并不是一个 AI 框架，也不是一个自动化系统。

它的本质是一个协议层设计。

更准确地说，它定义的是：

> 一个用于约束 AI Coding Agent 行为一致性的项目级状态协议。

它不试图改变 AI 的能力，而是改变 AI 进入项目时的方式。

---

# 9. 项目边界（Non-goals）

为了避免系统无限扩展，本项目明确不做以下事情：

- 不构建自动运行系统
- 不设计多 Agent 协调机制
- 不尝试增强模型智能本身
- 不引入复杂 orchestration 层

它的边界非常清晰：只做协议，不做系统。

---

# 10. 总结

这个项目的核心可以被简化为一句话：

> 通过将 AGENT.md 从“行为指令集合”重构为“项目状态重建协议”，实现 AI Coding Agent 在长期开发中的一致性与可恢复性。

它真正关注的不是 AI 能做什么，而是 AI 每一次进入项目时，能否以一致的方式重新理解这个世界。

---
