# AGENT.md

> 项目级状态重建协议 v1.0
>
> 本文档定义 AI Agent 进入此项目时的行为规则与状态访问协议。
> 它不是 prompt 集合，而是行为与状态的契约。

---

## 0. 核心概念

本项目是**状态驱动**的，不是 prompt 驱动的。

**仓库（repo）是唯一可信的现实来源**，不存在隐式状态，也不依赖模型的持久记忆。

所有认知必须从以下结构中恢复：

- `state/logs/` — 执行历史
- `state/tasks/` — 当前工作状态
- `state/memory/` — 稳定事实
- `state/wiki/` — 结构化知识
- `docs/` — 架构决策与设计文档

---

## 1. 项目初始化协议

### 判定标准

若以下任一条件成立，则项目结构视为**不完整**，需要初始化：

- `state/` 目录不存在
- `state/tasks/` 下没有任何 `.md` 文件
- `AGENT.md` 不存在于项目根目录

### 初始化操作

创建以下目录结构：

```
state/logs/
state/tasks/
state/memory/
state/wiki/
```

**规则：**
- 不得偏离此结构
- 不得添加任意目录
- 确保所有目录存在后再继续执行
- 若部分目录已存在，不要重建或覆盖

你是此项目的**执行 Agent**。

职责：
- 理解项目上下文

- 维护项目状态一致性
- 更新项目知识产物

## 3. 状态系统定义

项目是状态驱动的，状态以文件形式外置存储。

### 3.1 state/logs/
- 执行历史记录
- 记录发生了什么、为什么、结果如何
- **格式**：每个任务一条日志，时间戳开头

### 3.2 state/tasks/
- 当前工作状态
- 用单个文件 `status.md` 管理，标记语法：
  ```
  - [ ] TODO 事项
  - [/] 进行中事项
  - [x] 已完成事项
  ```
- 优先级用 `[P0]` `[P1]` `[P2]` 标注

### 3.3 state/memory/
- 仅存放**稳定、经过验证、可复用**的项目级事实
- **写入条件**：同一事实至少经过 2 次不同任务验证
- **每次写入 memory 必须在 logs 中有对应的验证记录**
- 不存放临时判断、未验证假设、单次观察

### 3.4 state/wiki/
- 结构化领域知识
- 概念模型、术语表、业务规则
- 仅当结构化知识积累到可独立成文时才写入

### 3.5 docs/
- 架构决策与设计理由
- 每个重要决策记录为 ADR（Architecture Decision Record）

---

## 4. 状态更新规则（关键）

每次任务执行完毕后，**必须**执行以下写回操作：

1. **更新 `state/logs/`** — 写入执行摘要
2. **更新 `state/tasks/status.md`** — 更新事项状态
3. **更新 `state/memory/`** — 仅当满足以下全部条件：
   - 信息是稳定的
   - 经过至少 2 次任务验证
   - 可复用于当前任务之外的场景
4. **更新 `state/wiki/`** — 仅当结构化知识出现
5. **更新 `docs/`** — 仅当架构/设计发生变化

**禁止：**
- ❌ 将 logs 当作 memory 使用
- ❌ 将假设当作事实写入 memory
- ❌ 在不同文件间重复同一信息
- ❌ 无理由覆盖已有 memory

---

## 5. 状态重建机制（Rehydration Protocol）

进入项目后，按以下顺序读取，以恢复一致认知：

```
Step 1: 读取 state/tasks/status.md
        → 理解当前工作进度与待办事项

Step 2: 读取 state/memory/
        → 获取稳定、已验证的基础事实

Step 3: 读取 docs/
        → 理解系统架构与历史设计决策

Step 4: 读取 state/wiki/
        → 补充结构化概念与领域知识（必要时）
```

**完成以上四步前，不得开始执行任何修改操作。**

---

## 6. 执行闭环

所有操作遵循固定闭环：

```
1. Rehydrate（恢复状态）
   → 按第 5 节顺序读取

2. Plan（制定计划）
   → 基于当前状态制定最小可执行计划

3. Execute（执行变更）
   → 实施计划中的变更

4. Persist（写回状态）
   → 按第 4 节规则更新所有状态文件
```

---

## 7. 一致性约束

- 永远不要无理由覆盖 memory
- 永远不要在不同文件间重复信息
- 永远不要将 logs 当作 memory
- 永远不要将假设当作事实
- 每次写回后，确保 state 各分类之间的信息不矛盾
- 不要因为「当前任务简单」而跳过 Persist 步骤

---

## 8. 输出规范

所有输出必须：

- 结构化
- 最小化
- 显式说明状态变更

推荐输出格式：

```
## Plan
- 步骤 1: ...
- 步骤 2: ...

## Execution
- 已完成: ...

## Result
- 状态: 成功/部分成功/失败
- 说明: ...

## State Updates
- logs: [文件路径] — 追加执行记录
- tasks: status.md — [事项] → done
- memory: [写入/未变更]
```

## 9. 系统哲学

本项目不是 prompt 驱动的。

它是**状态驱动**的。

仓库（repository）是记忆系统。

**一致性不依赖"智能"，而依赖结构。**
